title: Introduction

---

Relic is a self-hosted artifact repository that keeps its content in S3. A
typical installation is one binary, one PostgreSQL database and any
S3-compatible storage. On a single node, the binary can run alone with SQLite
and a local directory.

You manage Relic with the `relic` CLI, the web UI or the Relic API. Package
managers talk to it directly.

## What it serves

| Area | Contents |
| --- | --- |
| Repositories | npm, Maven and Gradle, Docker and OCI, Go, PyPI, Helm, NuGet, RubyGems, Cargo, Conan, Terraform, Hugging Face, Nix, Debian, RPM, Alpine and generic files, as local, remote (caching proxy) or virtual repositories. |
| Builds, release bundles, evidence | Records of what was built from what, where it was promoted, and who signed it (`relic build`, `relic release`, `relic evidence`). |
| Relic Scan | Catalogs packages and their licenses with Syft and finds their vulnerabilities with Grype. It also reports malicious packages, secrets (Gitleaks), misconfigurations (Trivy) and, optionally, licenses in files (ScanCode). Policies can block downloads (`relic security scan`, `relic security audit`). |

## Architecture

| Part | Role |
| --- | --- |
| `relic` server | The HTTP APIs and this web UI. |
| `relic server worker` | Runs background jobs: scanning, garbage collection, replication, webhook deliveries, cleanup policies, the storage check, and the trash can's and the audit log's retention. `relic server start --worker` runs the server and the worker in one process. |
| PostgreSQL or SQLite | Stores metadata: items, properties, builds, users, permissions and scan results. Use SQLite for a single node. |
| Object storage | Stores content once per SHA-256. Use S3-compatible storage (SeaweedFS is recommended) or a local directory. See [Storage](/docs/installation/storage/overview). |
