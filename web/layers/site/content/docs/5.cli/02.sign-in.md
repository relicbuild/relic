---
title: Sign in and contexts
description: relic auth login, saved contexts, and how the server and token are chosen.
---

Sign in to a server in the browser. The command prints a link and a code; open
the link, sign in (with a password or [single sign-on](/docs/guides/security/single-sign-on)),
check the code and approve:

```bash
relic auth login https://relic.example.com
```

Sign in with a user name instead. The command prompts for the password:

```bash
relic auth login https://relic.example.com --user alice
```

In a script, pass the password on standard input and save the context as `ci`:

```bash
echo "$PASSWORD" | relic auth login https://relic.example.com -u ci --password-stdin --context ci
```

A CI job signs in without a stored secret by exchanging the OIDC token its
platform issues, through a [workload identity](/docs/guides/security/workload-identities):

```bash
relic auth login https://relic.example.com --identity github --oidc-token "$ID_TOKEN"
```

That token lives an hour at most. Otherwise, `relic auth login` creates an access token. The token lasts 90 days by
default; set another lifetime with `--expires-days`, within the
[limits](/docs/guides/security/tokens#lifetimes). The command saves the token
and the server URL as a context in `relic/config.yaml` under your user
configuration directory (mode 0600): `~/.config` on Linux (`$XDG_CONFIG_HOME`
when it is set), `~/Library/Application Support` on macOS and `%AppData%` on
Windows. It never stores the password.

| Command | Does |
| --- | --- |
| `relic auth context list` | lists the contexts and marks the current one with `*` (tokens are not shown) |
| `relic auth context show` | shows the current context (its token is not shown) |
| `relic auth context use <name>` | switches contexts |
| `relic auth logout [<name>]` | revokes a context's token on its server and forgets the context; without a name, the current context |

Signing in again to a context replaces its token and revokes the previous one.

Every command takes the flags `--context`, `--url` and `--token`. Every command
also reads the environment variables `RELIC_URL`, `RELIC_TOKEN` and
`RELIC_CONFIG`. Flags take precedence over environment variables, and
environment variables take precedence over the saved context. A context's token
and certificate authority go only to that context's server: when `--url` or
`RELIC_URL` names another server, give its token with `--token` or
`RELIC_TOKEN`.

## Servers with a private certificate authority

`relic auth login` checks the server's certificate. When this machine trusts
it, the command signs in as above. A server that generates its own certificate
authority ([TLS](/docs/installation/configuration#tls)) needs one of these:

- `--ca-file` names the authority's certificate, `ca.crt`, which you get from
  the server's administrator.
- On a terminal, the command shows the authority's name and SHA-256 fingerprint
  and asks `Trust this authority for <host>? [y/N]`. Compare the fingerprint with
  the one the server logs at start before you answer `y`.

Sign in and trust the authority in `ca.crt`:

```bash
relic auth login https://relic.example.com --user alice --ca-file ca.crt
```

Without a terminal, or with `--password-stdin`, the command does not ask. It
fails and names the fingerprint, and you pass `--ca-file` instead. The context
keeps the authority, so later commands with that context trust it too.

## On the server's own machine

On a machine where `relic server setup` installed the service, a command
needs no sign-in while nothing names a server: no flag, no environment
variable, no saved context, and no config file chosen with `--config` or
`RELIC_CONFIG`. It then reaches the service at the address in
its settings file and signs in as the first administrator, with
`RELIC_ADMIN_USERNAME` and `RELIC_ADMIN_PASSWORD` from that file. It trusts
the `ca.crt` in the service's `RELIC_TLS_DIRECTORY`.

- The file is the service's `server.env`, or `/etc/relic/relic.env` for a
  system service. Only someone who can read it gets this access: the user who
  ran the setup, or root and the `relic` group for a system service.
- It stops working once the administrator's password is changed, because the
  file holds the first password only. Sign in with `relic auth login` then.
- `relic package setup` still needs a context: it gives the package manager a
  token, and this sign-in has none.
