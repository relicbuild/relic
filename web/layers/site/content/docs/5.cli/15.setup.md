---
title: Machine setup
description: relic server installs, runs and inspects the Relic server on a machine, with shell completion and the server as a systemd service.
---

`relic server setup` installs relic on this machine. It sets up the client
config, shell completion, and the server as a systemd service.

You choose only who owns the service. By default it is a service for your user.
With `--system`, run as root, it is a service for the whole machine.

The command lists every file and command it will touch, and asks before it
changes anything. `--yes` skips the question. Running it again changes nothing.
It leaves alone files that already hold the right content, and the plan marks
them `unchanged`.

The service needs systemd. On a machine without `systemctl`, such as macOS or
Windows, the command stops before it changes anything;
[run the server by hand](/docs/installation/single-binary/quick-start#run-by-hand)
there.

Install a user service:

```bash
relic server setup
```

Install a system service, for every user:

```bash
sudo relic server setup --system
```

To configure a package manager instead, use
`relic package setup <client> <repository>`
([Package managers](/docs/cli/package-managers)).

## What it sets up

| What | Where |
| --- | --- |
| Client config: contexts and tokens (`relic auth login` fills it) | `~/.config/relic/config.yaml` (under `$XDG_CONFIG_HOME` when it is set), mode 0600. Created empty if missing, and never rewritten. `--config` and `RELIC_CONFIG` choose another file. |
| Shell completion | bash: `~/.config/relic/completion.bash`, loaded from a marked block in `~/.bashrc`. zsh: `completion.zsh`, loaded from `~/.zshrc`. fish: `~/.config/fish/completions/relic.fish`. The shell is taken from `$SHELL`, or from `--shell`. |

Every run replaces the block in `~/.bashrc` and keeps the rest of the file.
The block looks like this:

```bash
# relic setup completion begin
# Completion for relic, written by relic server setup.
[ -f "$HOME/.config/relic/completion.bash" ] && . "$HOME/.config/relic/completion.bash"
# relic setup completion end
```

## The server as a service

By default, relic runs `relic server start --worker` as a systemd **user**
service. The server uses SQLite and the filesystem store
([Single node](/docs/installation/single-binary/quick-start)). The service
needs no root. It keeps running after you log out and across reboots
(`loginctl enable-linger`).

| What | Where |
| --- | --- |
| Settings, with a generated encryption key and admin password | `~/.config/relic/server.env`, mode 0600 |
| Unit | `~/.config/systemd/user/relic.service` (`Restart=always`) |
| Database and files | `~/.local/share/relic`, mode 0700 |
| Certificate authority and server certificate (`RELIC_TLS_DIRECTORY`) | `~/.config/relic/tls` |

The server listens on `127.0.0.1:8090` and serves HTTPS with a certificate
authority it generates ([TLS](/docs/installation/configuration#tls)).
`--listen` sets another address. The server serves metrics on
`127.0.0.1:8091` over plain HTTP. relic commands on this machine that reach the
service without a context trust its `ca.crt`
([On the server's own machine](/docs/cli/sign-in#on-the-servers-own-machine)).

Later runs keep the settings already in `server.env`. This means the encryption
key never changes while secrets encrypted with it exist. Later runs add any
missing settings, and `--listen` replaces the address.

To change any other [setting](/docs/installation/configuration), edit the
file. Setup restarts the service when the file or the unit changed, or when the
running server is another binary than the one on disk (after an upgrade), and
starts it otherwise.

Sign in as `admin`. The password is the value of `RELIC_ADMIN_PASSWORD` in
`server.env`. The command shows the authority's fingerprint and asks whether to
trust it; `--ca-file ~/.config/relic/tls/ca.crt` trusts it without asking:

```bash
relic auth login https://127.0.0.1:8090 --user admin
```

Check the service:

```bash
systemctl --user status relic
```

Follow the service's logs:

```bash
journalctl --user -u relic -f
```

### System service

`sudo relic server setup --system` installs the server the way ollama's
installer does. It creates:

- a `relic` system user with its home at `/var/lib/relic`
- the binary, copied to `/usr/local/bin/relic`
- the settings in `/etc/relic/relic.env` (mode 0640, group `relic`)
- the directory `/etc/relic/tls` for the certificate authority, owned by
  `relic` (`RELIC_TLS_DIRECTORY`)
- the unit `/etc/systemd/system/relic.service`

The service runs as `relic` and may write only to `/var/lib/relic` and
`/etc/relic/tls`. It starts
at boot, and systemd restarts it whenever it stops. Bash completion goes to
`/usr/share/bash-completion/completions/relic` for every user.

The system service gets no client config. `relic auth login` creates yours the
first time you sign in. Do not also run `relic server setup` as yourself: that
installs a second server, as a user service on the same port.

Check the service:

```bash
systemctl status relic
```

Follow the service's logs:

```bash
journalctl -u relic -f
```

## Status and settings

`relic server status` reports the service on this machine:

```text
╭──────────────────────────────────────────────────────────────────────────────────╮
│ This machine  user service · ~/.config/systemd/user/relic.service                │
│                                                                                  │
│ server      ● active (running)  since Sat 2026-10-03 06:30:55 +04 · pid 177655   │
│ address     https://127.0.0.1:8090  ✓ Relic v0.1.0                               │
│ metrics     http://127.0.0.1:8091/metrics                                        │
│ settings    ~/.config/relic/server.env  ✓ encryption key set                     │
│ database    sqlite ~/.local/share/relic/relic.db  1.6 MiB                        │
│ files       filesystem ~/.local/share/relic/objects  3.2 GiB in 1204 files       │
│ scanner db  ~/.local/share/relic/grype  812.4 MiB                                │
│ disk        60% free  1.1 TiB of 1.8 TiB                                         │
│ binary      ~/.local/bin/relic                                                   │
│ completion  ~/.config/relic/completion.bash                                      │
╰──────────────────────────────────────────────────────────────────────────────────╯
```

On a terminal, the states are coloured. Piped output has no colour codes.

The service state comes from systemd. The command asks the address for the
server's version, and reads the sizes from disk. For a PostgreSQL database or
an S3, Azure Blob Storage or Google Cloud Storage store, the report shows the
name (without credentials) but no size.

For a system service, only root and the `relic` group can read the settings
and data. Run `sudo relic server status` for the full report.

The command exits with status 1 when the service is not running or does not
answer. `-o json` prints the same report as JSON.

`relic server config` prints the service's settings, with keys, passwords,
secrets, tokens, connection strings, OTLP headers and the passwords in URLs
masked. `relic server config set` changes one setting and restarts the service,
also when the setting already has that value. It takes the `RELIC_` and `OTEL_`
variables of the [configuration reference](/docs/installation/configuration).
It refuses a name the server does not read, and a value the server would refuse
to start with, before it changes anything.

Print the settings:

```bash
relic server config
```

Change the listen address:

```bash
relic server config set RELIC_HTTP_LISTEN_ADDRESS=0.0.0.0:8090
```

With `--value-stdin`, the argument is the key alone and the value comes from
standard input, which keeps a password out of the shell history and the
process list. Set the admin password from a variable:

```bash
printf '%s' "$PASSWORD" | relic server config set RELIC_ADMIN_PASSWORD --value-stdin
```

## Stop

`relic server stop` stops the service on this machine. It names the service
and its process, then asks first. The answer defaults to no, and `--yes` skips
the question. The service stays enabled, so it starts again at the next boot.

Stop the service:

```bash
relic server stop
```

Stop it without asking:

```bash
relic server stop --yes
```

Start it again:

```bash
systemctl --user start relic.service
```

For a system service, run the commands with `sudo` and leave out `--user`.

## Uninstall

`relic server uninstall` reverses `relic server setup`. It stops and disables
the service and removes:

- the unit
- the shell completion, and its block in `~/.bashrc` or `~/.zshrc`
- the relic binary, when it is under your home directory

It lists what it will remove and asks first. `--yes` skips the question.

The command keeps the server's data, `server.env`, the certificate authority in
`~/.config/relic/tls` and the client config. `server.env` holds the encryption
key that the data needs. relic lists what it kept, with the size of the data.
`--purge` deletes these as well, and its question defaults to no.

Uninstall and keep the data:

```bash
relic server uninstall
```

Delete everything `relic server setup` created, without asking:

```bash
relic server uninstall --purge --yes
```

Uninstall the system service. This also removes `/usr/local/bin/relic` and the
bash completion for every user, and keeps `/etc/relic`, `/var/lib/relic` and
the `relic` user:

```bash
sudo relic server uninstall --system
```

With `--system`, `--purge` also deletes `/etc/relic/relic.env`,
`/var/lib/relic` and the `relic` user.
