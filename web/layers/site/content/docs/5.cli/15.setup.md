---
title: Machine setup
description: Install, run, inspect and remove the Relic server on a machine as a systemd service.
---

`relic server setup` installs the client config, shell completion, and the
server as a systemd service for your user, or with `--system` (as root) for the
whole machine. It lists every change and asks first (`--yes` skips the
question). Running it again changes nothing.

The service needs systemd. Without `systemctl` (macOS, Windows), the command
stops before changing anything;
[run the server by hand](/docs/installation/single-binary/quick-start#run-by-hand).

Install a user service:

```bash
relic server setup
```

Install a system service:

```bash
sudo relic server setup --system
```

To configure a package manager, use `relic package setup`
([Package managers](/docs/cli/package-managers)).

## What it sets up

| What | Where |
| --- | --- |
| Client config (`relic auth login` fills it) | `~/.config/relic/config.yaml`, or `--config` / `RELIC_CONFIG`. Created empty if missing, never rewritten. |
| Shell completion, for `$SHELL` or `--shell` | bash: `~/.config/relic/completion.bash`, loaded from `~/.bashrc`. zsh: `completion.zsh`, loaded from `~/.zshrc`. fish: `~/.config/fish/completions/relic.fish`. |

Each run replaces only the marked block in `~/.bashrc` or `~/.zshrc`. The bash
block:

```bash
# relic setup completion begin
# Completion for relic, written by relic server setup.
[ -f "$HOME/.config/relic/completion.bash" ] && . "$HOME/.config/relic/completion.bash"
# relic setup completion end
```

## The server as a service

The user service runs `relic server start --worker` on SQLite and the
filesystem store ([Single node](/docs/installation/single-binary/quick-start)),
without root. `loginctl enable-linger` keeps it running after logout and starts
it at boot.

| What | Where |
| --- | --- |
| Settings, with a generated encryption key and admin password | `~/.config/relic/server.env`, mode 0600 |
| Unit | `~/.config/systemd/user/relic.service` |
| Database and files | `~/.local/share/relic`, mode 0700 |
| Certificate authority and server certificate | `~/.config/relic/tls` |

The server serves HTTPS on `127.0.0.1:8090` (`--listen` changes it) with a
certificate authority it generates ([TLS](/docs/installation/configuration#tls)),
and metrics over HTTP on `127.0.0.1:8091`. relic commands on this machine
trust its `ca.crt`
([On the server's own machine](/docs/cli/sign-in#on-the-servers-own-machine)).

Later runs keep the settings in `server.env`, so the encryption key never
changes; they add missing ones. Setup restarts the service when the settings,
the unit or the binary changed.

Sign in as `admin` with the `RELIC_ADMIN_PASSWORD` from `server.env`, and
trust the authority's fingerprint when asked:

```bash
relic auth login https://127.0.0.1:8090 --user admin
```

Check the service:

```bash
systemctl --user status relic
```

Follow its logs:

```bash
journalctl --user -u relic -f
```

### System service

`sudo relic server setup --system` creates:

- a `relic` system user with its home at `/var/lib/relic`
- `/usr/local/bin/relic`
- the settings in `/etc/relic/relic.env` (mode 0640, group `relic`)
- `/etc/relic/tls` for the certificate authority
- the unit `/etc/systemd/system/relic.service`
- bash completion in `/usr/share/bash-completion/completions/relic`

The service runs as `relic`, may write only to `/var/lib/relic` and
`/etc/relic/tls`, and starts at boot. It gets no client config;
`relic auth login` creates yours. Do not also run `relic server setup` as
yourself: that installs a second server on the same port.

Check the service:

```bash
systemctl status relic
```

Follow its logs:

```bash
journalctl -u relic -f
```

```text

```

PostgreSQL and cloud object stores show no size. For a system service, run it
with `sudo`. The command exits with status 1 when the service is not running or
does not answer.

Print the service's settings, with secrets, keys, tokens and connection
strings masked:

```bash
relic server config
```

Change one setting and restart the service:

```bash
relic server config set RELIC_HTTP_LISTEN_ADDRESS=0.0.0.0:8090
```

`config set` takes the `RELIC_` and `OTEL_` variables of the
[configuration reference](/docs/installation/configuration). It refuses an
unknown `RELIC_` name, or a value the server would not start with, before
changing anything.

Set the admin password from standard input, keeping it out of the shell
history and the process list:

```bash
printf '%s' "$PASSWORD" | relic server config set RELIC_ADMIN_PASSWORD --value-stdin
```

## Stop

Stop the service after confirming (`--yes` skips the question). It starts
again at the next boot:

```bash
relic server stop
```

Start it again:

```bash
systemctl --user start relic.service
```

For a system service, use `sudo` and leave out `--user`.

## Uninstall

`relic server uninstall` stops the service and removes its unit, the shell
completion and its rc block, and the relic binary when it is under your home
directory. It asks first.

It keeps the data, `server.env` (which holds the encryption key the data
needs), `~/.config/relic/tls` and the client config. `--purge` deletes them
too.

Uninstall and keep the data:

```bash
relic server uninstall
```

Delete everything setup created, without asking:

```bash
relic server uninstall --purge --yes
```

Uninstall the system service, removing `/usr/local/bin/relic` and the bash
completion:

```bash
sudo relic server uninstall --system
```

It keeps `/etc/relic`, `/var/lib/relic` and the `relic` user. With `--purge`, it
deletes `/etc/relic/relic.env`, `/etc/relic/tls`, `/var/lib/relic` and the
`relic` user too.
