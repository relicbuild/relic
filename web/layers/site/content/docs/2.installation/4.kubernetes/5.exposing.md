---
title: Exposing Relic
description: Reach Relic from outside the cluster with an ingress, a NodePort or a LoadBalancer.
---

The server listens on the `relic` Service, port 443, and serves HTTPS. With
`tls.enabled` set to `false` it serves plain HTTP on port 80. The relic CLI,
package managers and Docker clients need one host name that serves every path.

## The server's certificate

By default each server pod generates its own certificate authority
([TLS](/docs/installation/configuration#tls)). A single node keeps it on the
data volume. With several replicas it lives in an `emptyDir`, so it changes
whenever a pod restarts, and each pod has a different one. Clients that verify
the server need one certificate for all pods: set `tls.existingSecret` to a
`kubernetes.io/tls` Secret. The chart mounts it at `/etc/relic/tls` and points
`RELIC_TLS_CERTIFICATE_FILE` and `RELIC_TLS_KEY_FILE` at `tls.crt` and
`tls.key`.

cert-manager is the recommended way to get that Secret, because Relic reads a
renewed certificate without a restart. This Certificate asks a cert-manager
issuer for one that holds the Service's names and the public host name:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: relic-server-tls
  namespace: relic
spec:
  secretName: relic-server-tls
  privateKey:
    algorithm: ECDSA
    size: 384
  dnsNames:
    - relic
    - relic.relic
    - relic.relic.svc
    - relic.relic.svc.cluster.local
    - relic.example.com
  issuerRef:
    kind: ClusterIssuer
    name: internal-ca
```

Save it as `certificate.yaml` and create it:

```bash
kubectl apply -f certificate.yaml
```

Then point the chart at the Secret:

```yaml
tls:
  existingSecret: relic-server-tls
```

Without `tls.existingSecret`, the chart adds the Service's names and the ingress
hosts to the generated certificate. `tls.hostnames` adds more names.

## Ingress with TLS

```yaml
ingress:
  enabled: true
  className: nginx
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "0"
  hosts:
    - host: relic.example.com
  tls:
    - hosts: [relic.example.com]
      secretName: relic-tls
```

Raise the ingress controller's body size limit, or large uploads and Docker layers
fail. The example above removes the limit.

While `tls.enabled` is on, the chart adds the annotation
`nginx.ingress.kubernetes.io/backend-protocol: HTTPS`, so ingress-nginx connects
to the server over HTTPS. An annotation you set yourself takes precedence. For
another ingress controller, configure an HTTPS backend in its own way, or set
`tls.enabled` to `false`.

Relic trusts `X-Forwarded-*` headers only from the addresses in `trustedProxies`.
Narrow that setting to the ingress controller's pod CIDR.

## NodePort

Use a NodePort for a lab or a single-node cluster:

```yaml
service:
  type: NodePort
  nodePort: 30880
```

Relic is then at `https://<node-ip>:30880`. If you leave `nodePort` empty,
Kubernetes picks the port. Add the node's name or address to `tls.hostnames`,
or put it in the certificate of `tls.existingSecret`.

## LoadBalancer

```yaml
service:
  type: LoadBalancer
```

The server serves HTTPS on the load balancer's port 443. Give it a certificate
that clients trust with `tls.existingSecret`. To terminate TLS in a proxy in
front of the load balancer instead, set `tls.enabled` to `false` and list that
proxy in `trustedProxies`.

## Network policy

`networkPolicy.allowServerAccessFrom` lists the NetworkPolicy peers that can
reach the server. Left empty, it admits everyone. Once set, it admits only the
peers it lists, so include the ingress controller's namespace:

```yaml
networkPolicy:
  allowServerAccessFrom:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress-nginx
```

See [Hardening](/docs/installation/kubernetes/hardening).
