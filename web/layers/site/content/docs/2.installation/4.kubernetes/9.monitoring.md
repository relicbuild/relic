title: Monitoring
description: Collect metrics, traces and logs and get dashboards with the chart, using its own monitoring stack or yours.

Every Relic pod serves Prometheus metrics at `/metrics` on port 8091. This port is
separate from the one an ingress exposes. The [Monitoring guide](/docs/guides/monitoring)
explains the metrics, traces and alerts.

## Bundled stack

`monitoringStack.enabled` installs a monitoring stack next to Relic, from the
official charts:

| Chart | Contents |
| --- | --- |
| kube-prometheus-stack | The Prometheus Operator, Prometheus (with exemplar storage, keeping 15 days on a 20Gi volume), Alertmanager, Grafana, kube-state-metrics and node-exporter. |
| Tempo | Traces, in one process. |
| Loki | Logs, in one process, with filesystem storage. |
| Alloy | Ships the namespace's pod logs to Loki. Receives Relic's traces over OTLP and passes them to Tempo. |

Once the stack is installed:

- Relic sends traces to Alloy itself. It sends 10% of traces, or all traces from a
  caller that is already tracing.
- Prometheus scrapes Relic and loads its alert rules.
- Grafana gets Relic's seven dashboards in the *Relic* folder, CloudNativePG's
  dashboard, and Tempo and Loki datasources that link to each other:
  - a latency panel's exemplar opens its trace,
  - a trace opens its log lines,
  - a log line's `trace_id` opens its trace.

Install Relic with the bundled stack:

```bash
helm install relic helm/relic -n relic --create-namespace --set monitoringStack.enabled=true --set credentials.encryptionKey="$RELIC_ENCRYPTION_KEY" --set credentials.adminPassword="$RELIC_ADMIN_PASSWORD"
```

To also collect PostgreSQL's and SeaweedFS's own metrics, turn on monitoring in
their charts:

```yaml
monitoringStack:
  enabled: true
postgresql:
  cluster:
    monitoring:
      enabled: true
seaweedfs:
  global:
    seaweedfs:
      monitoring:
        enabled: true
```

To open Grafana, forward a local port to its Service:

```bash
kubectl -n relic port-forward svc/relic-grafana 3000:80
```

Print the Grafana admin password:

```bash
kubectl -n relic get secret relic-grafana -o jsonpath='{.data.admin-password}' | base64 -d
```

The chart generates this password once and keeps it across upgrades. Values for
the subcharts pass through under `kube-prometheus-stack`, `tempo`, `loki` and
`alloy`. To expose Grafana, set `kube-prometheus-stack.grafana.ingress.*`.

This Prometheus selects every ServiceMonitor, PodMonitor and rule in the cluster,
because the dependencies' monitors carry no release label. If your cluster already
runs a Prometheus, use that one instead, as described below.

### Turning it on for an existing release

`helm upgrade` installs no CRDs, so you apply the Prometheus Operator's CRDs once
yourself. Until they exist, the chart stops and prints the command to apply them.

Download the kube-prometheus-stack chart:

```bash
helm pull prometheus-community/kube-prometheus-stack --version 92.10.1 --untar -d /tmp
```

Apply its CRDs:

```bash
kubectl apply --server-side -f /tmp/kube-prometheus-stack/charts/crds/crds/
```

Upgrade the release with the stack turned on:

```bash
helm upgrade relic helm/relic -n relic --reset-then-reuse-values --set monitoringStack.enabled=true
```

## Your own stack

Leave `monitoringStack.enabled` off and configure each component:

| Component | Settings |
| --- | --- |
| Prometheus Operator | The chart adds a ServiceMonitor and a PrometheusRule when the `monitoring.coreos.com/v1` API exists. Set the labels your Prometheus selects with `metrics.serviceMonitor.labels` and `metrics.prometheusRule.labels`. Point the runbook links at your Relic with `metrics.prometheusRule.runbookBaseURL`. |
| Grafana | `grafana.dashboards.enabled` renders the dashboards as ConfigMaps for the dashboard sidecar (`grafana.dashboards.label`, `.folder`). To import them by hand, use the files in `deploy/observability/grafana/dashboards`. |
| Traces | Set `tracing.otlpEndpoint` to an OTLP over HTTP endpoint, such as `http://otel-collector.observability:4318`. `tracing.sampler` and `tracing.samplerArg` set the sampler. |
| Logs | A collector that ships pod logs needs no extra settings. Relic's log lines are JSON with `trace_id` and `span_id`. `logging.otlp` also sends them over OTLP. |
