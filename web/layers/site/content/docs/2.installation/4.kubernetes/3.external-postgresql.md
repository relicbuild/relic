---
title: External PostgreSQL
description: Run Relic from the chart against a PostgreSQL database you already operate.
---

To use your own database, turn off the `cnpg/cluster` dependency and the bundled
CloudNativePG operator, and give Relic a database URL.

1. Create a database and a user that owns it. Relic is tested on PostgreSQL 18.
   It applies its migrations at startup.
2. Create the `relic` namespace:

   ```bash
   kubectl create namespace relic
   ```

   Create a Secret in it with the database URL. You can also put the admin
   password and the encryption key in it:

   ```bash
   kubectl -n relic create secret generic relic \
     --from-literal=databaseURL='postgres://relic:<password>@<db-host>:5432/relic?sslmode=require' \
     --from-literal=adminPassword='<admin-password>' \
     --from-literal=encryptionKey="$(openssl rand -base64 32)"
   ```

3. Put these settings in `values.yaml`:

   ```yaml
   postgresql:
     enabled: false
   postgresql-operator:
     enabled: false
   existingCredentialsSecret: relic
   ```

4. Install Relic with your values:

   ```bash
   helm install relic oci://ghcr.io/relicbuild/charts/relic --version X.Y.Z -n relic -f values.yaml
   ```

SeaweedFS stays on, and its S3 keys still come from its own Secret. To replace
SeaweedFS as well, add the values from
[External object storage](/docs/installation/kubernetes/external-object-storage)
and put the S3 keys in the same Secret.

If you prefer the chart to create the Secret, leave out `existingCredentialsSecret`.
Set `credentials.databaseURL` and the other credential values instead.

## Production database

- Take point-in-time-recovery backups. Keep a copy of `encryptionKey` separate
  from them. If the server finds sealed data but no key, or a different key, it
  does not start. See [Secrets at rest](/docs/guides/operations#secrets-at-rest).
- Use `sslmode=require` or stricter.
- Allow enough connections for every server and worker pod.
