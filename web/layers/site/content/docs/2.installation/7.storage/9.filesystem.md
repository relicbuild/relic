---
title: Filesystem
description: Store artifact content in a local directory instead of an S3 service, on a single node.
---

```ini
RELIC_OBJECT_STORAGE_TYPE=filesystem
RELIC_OBJECT_STORAGE_PATH=/var/lib/relic/objects
```

With this store, Relic ignores the S3 settings (`RELIC_OBJECT_STORAGE_ENDPOINT`,
keys, buckets). The server and the worker must see the same directory, so both
run on one host.

## Layout

| Directory | Holds |
| --- | --- |
| `artifacts/` | Content under `sha256/<aa>/<bb>/<sha256>`, as in the S3 `artifacts` bucket. |
| `temporary/` | Uploads in progress, as in the S3 `temporary` bucket. |
| `staging/` | Files being written. Each write lands here first. Once the file is complete, Relic renames it into `artifacts/` or `temporary/`, so a reader never sees a partial file. |

Relic creates the directories at start. When Relic copies a file within the
store, it uses a hard link if the filesystem allows one.

## Requirements

- Local disk. On Linux, Relic refuses to start when the directory is on NFS,
  SMB/CIFS, FUSE, NCP, AFS, Coda, 9P, CephFS or Lustre. On macOS and Windows, it
  does not check. Renames and `fsync` on those filesystems do not give the
  guarantees the store needs.
- One filesystem for the whole directory. Renames are atomic only when
  `staging/` and its targets are on the same filesystem.
- The user Relic runs as can write to the directory (UID 65532 in the image).

## Expiry

A crash can leave partial uploads in `temporary/` and `staging/`. On every run
(`RELIC_GARBAGE_COLLECTION_INTERVAL`), the worker's garbage collection deletes
files there that are older than one day. `relic_gc_deleted_temporary_files_total`
counts them.

## Backups

Back up the database first, then copy `artifacts/` (`rsync -a`, or a filesystem
snapshot). You do not need to copy `temporary/` or `staging/`.
[Backup](/docs/guides/operations#backup) explains why the order matters.
