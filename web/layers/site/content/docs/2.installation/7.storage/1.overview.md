Relic keeps artifact content in object storage and everything else in the
database: PostgreSQL, or SQLite on a single node.
Object storage is an S3-compatible service (`RELIC_OBJECT_STORAGE_TYPE=s3`,
the default), Azure Blob Storage (`azure`), Google Cloud Storage (`gcs`), or a
local directory on a single node
([Filesystem](/docs/installation/storage/filesystem)). Relic reaches S3 storage
only through the S3 API. Any service that implements the operations listed below
works.

- [SeaweedFS](/docs/installation/storage/seaweedfs) (recommended for self-hosted storage)
- [Amazon S3](/docs/installation/storage/amazon-s3)
- [Cloudflare R2](/docs/installation/storage/cloudflare-r2)
- [MinIO](/docs/installation/storage/minio)
- [Google Cloud Storage](/docs/installation/storage/google-cloud-storage)
- [Azure Blob Storage](/docs/installation/storage/azure-blob-storage)
- [Backblaze B2](/docs/installation/storage/backblaze-b2)
- [Other S3-compatible services](/docs/installation/storage/other): Ceph, Wasabi, DigitalOcean Spaces, Garage
- [Filesystem](/docs/installation/storage/filesystem): a local directory, one node only

## What goes where

| Database | Object storage |
| --- | --- |
| Repositories, items, paths, properties, checksums, builds, users, tokens, permissions, scan results, the job queue. | File content, stored once per SHA-256. |

## Buckets

| Bucket | Holds | Behaviour |
| --- | --- | --- |
| `artifacts` | Content under `sha256/<aa>/<bb>/<sha256>` | Objects never change. Identical files share one object, so copies, moves and promotions use no extra storage. The worker's garbage collection deletes an object once no item has referenced it for `RELIC_GARBAGE_COLLECTION_GRACE_PERIOD` (default one hour). |
| `temporary` | Uploads in progress | Relic streams each upload into `temporary` and computes its checksums. If the content is new, Relic copies the object into `artifacts` server-side. Then it deletes the `temporary` object. Garbage collection deletes `temporary` objects older than a day, which a crash or an abandoned upload leaves behind. |

The `artifacts` bucket also holds `layout.json`, which records the version of
this layout (`{"version":1}`). Relic writes it when it first uses a store, and
refuses to start on a store that records another version, so a release with
a different layout cannot write into your storage by mistake. Keep the file in
backups and copies of the bucket.

Clients never talk to object storage. Every download streams through Relic, so
only Relic needs network access to the storage endpoint. Run Relic close to the
storage: with a cloud provider, every download is a read from the bucket. Once a
day, the worker's storage check also lists `artifacts` and reads up to 10 GiB of
content back to verify it.

A file can be up to 5 TiB when the client sends its size (`Content-Length`),
as package clients do. An upload without a size, such as a chunked transfer,
can be up to 64 GiB. Relic uploads in parts of 5 MiB or more, and holds two
parts of each upload in memory.

## Bucket requirements

- Create both buckets before the first start. Relic never creates buckets. Only
  the Helm chart's bundled SeaweedFS and the Compose stack create them.
- Use two different buckets on the same endpoint. One key pair must be able to
  read and write both, because Relic copies objects from `temporary` to
  `artifacts` server-side.
- On both buckets, expire incomplete multipart uploads after one day. They do
  not appear in listings, so Relic cannot remove them. An expiry rule for
  `temporary` objects is optional: Relic deletes those older than a day.
- Turn off versioning and object lock on `artifacts`. Garbage collection deletes
  objects. With versioning on, deleted data stays as old versions and still
  costs storage. If you must keep versioning, add a rule that expires noncurrent
  versions. Object lock makes deletes fail.
- Keep both buckets private. Relic signs every request, so nothing needs public
  access.
- The storage service handles encryption at rest. Unless
  `RELIC_OBJECT_STORAGE_SSE` is set, Relic sends no encryption headers, so the
  bucket's default encryption applies.

## Permissions

| Operation | Bucket | Why |
| --- | --- | --- |
| `PutObject`, `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, `AbortMultipartUpload` | `temporary` | Stage uploads. |
| `CopyObject`, `UploadPartCopy` (over 5 GiB) | `temporary` to `artifacts` | Move an upload to its content address. |
| `GetObject` with byte ranges, `HeadObject` | both | Downloads, range requests, scanning, the readiness check, the storage check. |
| `ListObjectsV2` | both | Garbage collection lists `temporary` to delete old uploads. The daily storage check lists `artifacts` to compare it with the database. |
| `DeleteObject` | both | Clean up staged uploads; garbage collection. |

The readiness check (`/readyz`) sends `HeadObject` for `readyz/probe`, a key that
does not exist in the `artifacts` bucket. It expects "not found". If the service
answers "access denied" instead, Relic stays unready. On Amazon S3 this happens
when the key lacks `s3:ListBucket`.

## Connection settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `RELIC_OBJECT_STORAGE_ENDPOINT` | (empty) | The S3 API's base URL, with scheme. Empty means Amazon S3. |
| `RELIC_OBJECT_STORAGE_REGION` | `us-east-1` | The region Relic signs requests for (Signature Version 4). |
| `RELIC_OBJECT_STORAGE_ACCESS_KEY`, `RELIC_OBJECT_STORAGE_SECRET_KEY` | (empty) | A static key pair. Without one, Relic uses the AWS default credential chain. |
| `RELIC_OBJECT_STORAGE_ARTIFACTS_BUCKET`, `RELIC_OBJECT_STORAGE_TEMPORARY_BUCKET` | `artifacts`, `temporary` | Bucket names. They must differ. |

In the Helm chart, the endpoint, region and bucket names are `objectStorage.*` values. The
key pair is `objectStorageAccessKey` and `objectStorageSecretKey` in the Secret.
See [Helm](/docs/installation/kubernetes/external-object-storage).

## What Relic does not support

The code fixes these behaviours. No setting changes them, except the ones an
item names. Check them against a provider before you choose it.

- **Path-style requests with an endpoint.** When `RELIC_OBJECT_STORAGE_ENDPOINT`
  is set, Relic addresses buckets as `<endpoint>/<bucket>/<key>`. Without it,
  Relic talks to Amazon S3 with virtual-hosted-style URLs. There is no setting
  for virtual-hosted-style URLs on another endpoint.
- **No session token setting.** Without a static key pair, Relic reads the AWS
  default credential chain: `AWS_*` environment variables, shared credential
  files, IAM roles for service accounts, EKS Pod Identity and instance profiles.
- **No TLS options.** Relic verifies `https://` endpoints against the system CA
  bundle. There is no setting for a private CA or for skipping verification. The
  Go runtime reads the standard `SSL_CERT_FILE` and `SSL_CERT_DIR` variables,
  which replace the default bundle. The Helm chart has no value to mount such a
  file.
- **No signing options.** Relic uses the AWS SDK for Go v2, which adds CRC32
  checksums to uploads. On a service that rejects the SDK's newer checksum
  headers, uploads fail unless `RELIC_OBJECT_STORAGE_CHECKSUM` is
  `when_required`, which sends checksums only where S3 requires them. Test an
  upload before you commit to a service.
- **No ACL headers.** The bucket's defaults apply. Encryption and the storage
  class are set for every write with `RELIC_OBJECT_STORAGE_SSE`,
  `RELIC_OBJECT_STORAGE_SSE_KMS_KEY_ID` and `RELIC_OBJECT_STORAGE_STORAGE_CLASS`.

## Sizes and throughput

- Relic streams uploads to storage as multipart uploads in parts of 5 MiB, or
  larger for files over about 49 GiB so that no upload needs more than 10,000
  parts, with two parts in flight per upload. Memory use stays bounded whatever
  the file size.
- Relic moves objects up to 5 GiB into `artifacts` with one `CopyObject`. Larger
  objects use `UploadPartCopy` in 512 MiB parts.
- Range requests pass straight through to `GetObject`.

## Moving to another provider

Object keys are the same on every provider.

1. Create the buckets on the new service, with the settings above.
2. Copy the `artifacts` bucket with any S3 sync tool, for example `rclone sync`.
3. Stop the server and the worker. Run the copy once more. Point
   `RELIC_OBJECT_STORAGE_*` at the new service, then start the server and the
   worker again.

You do not need to copy the `temporary` bucket.

## Backups

Back up the database first, then copy `artifacts`. [Backup](/docs/guides/operations#backup)
explains why the order matters.
