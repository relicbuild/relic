## Get the image

Every release publishes a signed image for linux/amd64 and linux/arm64 to
`ghcr.io/relicbuild/relic`, and the same image to Docker Hub as
`relicbuild/relic`. The image is tagged with the release (`v1.2.3`), its
minor version (`1.2`) and `latest`; a pre-release (`v1.2.3-beta.1`) is tagged
with the release only. Pull the current release:

```bash
docker pull ghcr.io/relicbuild/relic:vX.Y.Z
```

Check its signature with cosign (optional):

```bash
cosign verify ghcr.io/relicbuild/relic:vX.Y.Z --certificate-oidc-issuer https://token.actions.githubusercontent.com --certificate-identity-regexp '^https://github.com/relicbuild/relic/'
```

Or build it from a checkout of the release's tag:

```bash
docker build --build-arg VERSION=vX.Y.Z -t ghcr.io/relicbuild/relic:vX.Y.Z .
```

One image runs every part. The command you pass selects which one:

| Command | What it does |
| --- | --- |
| `server start` (the default) | Applies migrations, then serves the HTTP APIs and the web UI over HTTPS on `RELIC_HTTP_LISTEN_ADDRESS` (`:8090`). `--no-tls` serves plain HTTP. |
| `server start --worker` | Runs the server and the background jobs in one process, for a single node. |
| `server worker` | Applies migrations, then runs background jobs. |
| `server migrate` | Applies migrations and exits. |

The binary in the image has the web UI built in. The image also contains Syft,
Grype, Gitleaks, Trivy and the `relic-indexer` builds. It is distroless and runs
as a non-root user. It includes the Debian CA bundle, which Relic uses for HTTPS
connections to object storage and upstreams. `ghcr.io/relicbuild/relic` is also
the Helm chart's default repository.

## Run one container

Put the settings in an env file outside the repository, for example
`relic.env` with mode 0600. It holds these lines:

```ini
RELIC_DATABASE_URL=sqlite:///var/lib/relic/data/relic.db
RELIC_OBJECT_STORAGE_TYPE=filesystem
RELIC_OBJECT_STORAGE_PATH=/var/lib/relic/data/objects
RELIC_ADMIN_PASSWORD=<admin-password>
RELIC_ENCRYPTION_KEY=<openssl rand -base64 32>
```

Start the container with the server and the worker in one process:

```bash
docker run -d --name relic --restart unless-stopped --env-file relic.env -p 8090:8090 \
  -v relic-data:/var/lib/relic/data -v relic-grype:/var/lib/relic/grype -v relic-tls:/etc/relic/tls \
  ghcr.io/relicbuild/relic:vX.Y.Z server start --worker
```

The server serves HTTPS with a certificate authority it generates in
`/etc/relic/tls` ([TLS](/docs/installation/configuration#tls)). Copy the
authority's certificate out of the container:

```bash
docker cp relic:/etc/relic/tls/ca.crt .
```

Trust `ca.crt` in your browser or system, open `https://localhost:8090` and
sign in as `admin`. Then [sign in with the relic CLI](/docs/cli/sign-in) with
`--ca-file ca.crt`.

| Volume | Holds |
| --- | --- |
| `relic-data` | The SQLite database and the content. Back it up together with `relic.env` ([Limits and backups](/docs/installation/single-binary/operations)). |
| `relic-grype` | Grype's vulnerability database. Without it, the worker downloads it again after every restart. |
| `relic-tls` | The certificate authority and the server certificate. Without it, a new container creates a new authority, and clients have to trust it again. |

Use named volumes, or a bind mount owned by uid 65532 (the image's `nonroot`
user). To reach the server by another name, such as `relic.example.com`, add
the name to `RELIC_TLS_HOSTNAMES`, or give Relic your own certificate with
`RELIC_TLS_CERTIFICATE_FILE` and `RELIC_TLS_KEY_FILE`. Behind a reverse proxy
that terminates TLS, run `server start --worker --no-tls` and list the proxy in
`RELIC_TRUSTED_PROXIES` ([Behind a reverse proxy](/docs/guides/operations#behind-a-reverse-proxy)).

To back up the database, run `relic server database backup` inside the container:

```bash
docker exec relic /relic server database backup /var/lib/relic/data/backup-$(date +%F).db
```
