---
title: Limits and backups
description: What a single node cannot do, how to back it up and restore it, and how to move it to PostgreSQL.
---

## Limits

- Only one host may use the data. `relic server start` and `relic server worker`
  may run as two processes on the same host, but never on two hosts. Give the
  second process its own `RELIC_METRICS_LISTEN_ADDRESS`, such as `:8092`. Both
  default to `:8091`, and the one that starts second exits.
- The data must be on a local disk. On Linux, Relic refuses to start when the
  database or the content is on NFS, SMB/CIFS, FUSE, NCP, AFS, Coda, 9P, CephFS
  or Lustre. On macOS and Windows, it does not check.
- On Windows, the lock file beside the SQLite database does not work. Start the
  server first, and the worker once the server is up, so that only one process
  applies the migrations.
- SQLite allows one writer at a time. Reads continue while a write runs. Many
  concurrent pushes wait in a queue.
- `RELIC_DATABASE_STATEMENT_TIMEOUT` and `RELIC_DATABASE_MAX_CONNECTIONS` apply
  to PostgreSQL only.
- Text sorts by byte, and case-insensitive search folds ASCII letters only.

`relic_disk_free_bytes`, `relic_disk_size_bytes` and
`relic_db_sqlite_file_bytes` measure the volume and the database. The
RelicDiskSpaceLow alert fires when less than 10% of the volume is free
([Monitoring](/docs/guides/monitoring#relicdiskspacelow)).

## Backups

Back up three things: the database, the content, and `RELIC_ENCRYPTION_KEY`.
Without the key, Relic cannot read the sealed secrets in the database.

With the user service from `relic server setup`, the data is in
`~/.local/share/relic` and the key is in `~/.config/relic/server.env`.

While Relic runs, back up the database:

```bash
relic server database backup --database-url "sqlite://$HOME/.local/share/relic/relic.db" /backups/relic-$(date +%F).db
```

Then copy the content:

```bash
rsync -a ~/.local/share/relic/objects/artifacts/ /backups/objects/
```

Copy the settings too, because they hold `RELIC_ENCRYPTION_KEY`. Keep them
apart from the database and content backups, so that one stolen copy does not
hold both the sealed secrets and their key
([Secrets at rest](/docs/guides/operations#secrets-at-rest)):

```bash
cp ~/.config/relic/server.env /secure/relic-settings/
```

Copy the certificate authority as well. Without it, Relic creates a new one,
and every client has to trust that one
([TLS](/docs/installation/configuration#tls)):

```bash
cp -r ~/.config/relic/tls /secure/relic-settings/
```

With `--system`, the data is in `/var/lib/relic`, the settings are in
`/etc/relic/relic.env` and the certificate authority is in `/etc/relic/tls`.

`relic server database backup` writes a consistent snapshot while the server and
the worker keep running. It refuses to overwrite an existing file.

Back up the database first, then the content. Content added in between is only
unreferenced in the copy. Content missing from the copy would break items.

To restore:

1. Stop Relic.
2. Put the snapshot in place of `relic.db`, and delete `relic.db-wal` and
   `relic.db-shm` if they exist.
3. Copy the content back under `objects/artifacts/`.
4. Start Relic.

## Moving between PostgreSQL and SQLite

`relic server database copy` copies every table into an empty database. Use it
to move from SQLite to PostgreSQL when an installation outgrows one node, or to
move back. For example:

```bash
relic server database copy --from sqlite:///var/lib/relic/data/relic.db \
  --to 'postgres://relic:<password>@db:5432/relic?sslmode=require'
```

1. Stop the server and the worker. Nothing may write to the source.
2. Run the copy. It migrates the target and refuses a target that already has
   data. It copies in one transaction, then compares the row counts of every
   table.
3. Point `RELIC_DATABASE_URL` at the target and start Relic with the same
   `RELIC_ENCRYPTION_KEY`.

The content stays where it is. To move it from the filesystem store to S3 as
well, copy `objects/artifacts/` into the artifacts bucket before you start Relic
on S3. The keys are the same in both stores.

The copy does not include background jobs. The worker schedules its periodic
jobs again.
