## Backup

Back up PostgreSQL and the `artifacts` bucket. The `temporary` bucket and Grype's
database can be rebuilt, so they need no backup. For a single node with SQLite or
the filesystem store, see [Limits and backups](/docs/installation/single-binary/operations#backups).

1. Back up PostgreSQL **first**. Use a snapshot, a base backup with WAL, or
   `pg_dump`.
2. Then copy the `artifacts` bucket with any S3 sync tool, such as `rclone sync`.

Content is immutable. Garbage collection deletes only content that nothing has
referenced for the grace period (`RELIC_GARBAGE_COLLECTION_GRACE_PERIOD`, default
1 hour). If the bucket copy finishes within the grace period, it therefore holds
every blob the database backup refers to. If the copy takes longer, stop the
worker while it runs (`kubectl scale deploy/relic-worker --replicas=0`). Extra
blobs in the copy are harmless, because garbage collection removes them after a
restore.

Keep a copy of `RELIC_ENCRYPTION_KEY` separate from the backups. See
[Secrets at rest](#secrets-at-rest).

### Restore

1. Stop the server and the worker.
2. Restore PostgreSQL to the chosen point.
3. Restore the `artifacts` bucket from a copy taken **after** that point. Create
   an empty `temporary` bucket.
4. Start the server, then the worker.

## Upgrades

Migrations run at startup and only go forward. Upgrade the server first, then
the worker. Old servers keep working during the rollout. Relic does not support
downgrades, so restore from a backup instead. For Helm, see
[Upgrades](/docs/installation/kubernetes/upgrades).

## Routine operations

| Task | Behaviour |
| --- | --- |
| Garbage collection | Runs in the worker every `RELIC_GARBAGE_COLLECTION_INTERVAL` (10 minutes). It deletes content that no item has referenced for `RELIC_GARBAGE_COLLECTION_GRACE_PERIOD`. It holds no database transaction while it deletes objects, and a deploy of the same content during a collection keeps it. Content in the trash can stays referenced until you empty the trash can or its retention (`RELIC_TRASH_RETENTION`, 14 days) runs out. Container image layers pushed without a manifest that uses them are deleted after a day. |
| Storage check | Runs in the worker once a day, and on demand with **Check storage** on the System page or `relic storage check`. It compares object storage with the database. Content no item knows about, older than the garbage collection grace period, is handed to garbage collection. Content that is missing or of the wrong size is reported, and up to 10 GiB of stored content is re-hashed per run, the content checked longest ago first. Problems raise the RelicContentIntegrity alert, and the report is the `storage_check` job's output on the System page. |
| Audit log purge | Runs in the worker once a day. It deletes audit events older than `RELIC_AUDIT_RETENTION` (365 days) ([Audit log](/docs/guides/security/audit-log)). |
| Relic Scan | Needs `syft` and `grype`. The image contains both. Without them, scanning turns itself off. Persist `/var/lib/relic/grype` so that Relic does not download the vulnerability database again on every restart. |
| Logs | JSON on stderr. Every request line has a `request_id`, and traced requests also have a `trace_id`. Credentials are never logged. For metrics, traces, dashboards and alerts, see [Monitoring](/docs/guides/monitoring). |

## Behind a reverse proxy

The server serves HTTPS by default. Behind a proxy that terminates TLS, either
start it with `--no-tls` so it serves plain HTTP, or let the proxy connect to it
over HTTPS ([TLS](/docs/installation/configuration#tls)).

Relic trusts `X-Forwarded-Proto` and `X-Forwarded-For` only from the addresses in
`RELIC_TRUSTED_PROXIES`. It strips these headers from every other client. List
the proxy that terminates TLS in that setting. If you don't, Relic generates
`http://` URLs and sets session cookies without `Secure`. It also cannot tell
clients apart, because sign-in backoff and the logs see only the proxy. Over
HTTPS, every response carries `Strict-Transport-Security: max-age=31536000`.

Sign-in backoff slows down password guessing. A client that sends more than 20
wrong passwords within 10 minutes must wait before its next password attempt.
The wait starts at one second and doubles up to five minutes. During the wait,
the client gets `429` with a `Retry-After` header. Relic counts per client
address, so nobody can lock out another user. Tokens are not throttled.

## Memory and concurrent uploads

In a container with a memory limit, Relic sets Go's soft memory limit to 90% of
it, unless `GOMEMLIMIT` sets one. Each upload in flight to S3-compatible storage
holds up to 40 MiB, so Relic runs (soft limit − 256 MiB) ÷ 40 MiB uploads at
once, between 4 and 64, and further uploads wait. Without a limit, 16 run at
once. A 1 GiB memory limit, for example, allows 16; size the server's memory
(`server.resources.limits.memory` in the chart) for the uploads you expect.

## Secrets at rest

When `RELIC_ENCRYPTION_KEY` is set, Relic seals the secrets it keeps in the
database (PostgreSQL or SQLite) with AES-256-GCM. These secrets are:

- token signing keys
- every key pair, such as the ones that sign Alpine, Debian and RPM indexes and
  release manifests
- remote repository and replication passwords
- LDAP manager passwords
- identity providers' OIDC client secrets and SAML keys
- webhook secrets

When it starts, Relic seals the secrets stored before the key was set. Set the
same key on the server and the worker.

Keep the key separate from the database backups, and keep a copy you can
restore. The server does not start if it finds sealed signing keys but has no
key, or has a different key. Without the key, Relic stores these secrets
unencrypted and logs a warning at startup.

## Health

- `/healthz`: the process is alive.
- `/readyz`: the database and object storage answer.
- **Administration → System** shows both checks, plus storage, background jobs
  and scanner state. It also has a button that runs garbage collection now.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `/readyz` answers "database unavailable" | `RELIC_DATABASE_URL`, network policies to PostgreSQL, connection limits. |
| `/readyz` answers "object storage unavailable" | `RELIC_OBJECT_STORAGE_ENDPOINT`, `RELIC_OBJECT_STORAGE_REGION`, the key pair, and whether the artifacts bucket exists. On Amazon S3, the key also needs `s3:ListBucket`. See [Amazon S3](/docs/installation/storage/amazon-s3#iam-policy). |
| Relic does not start and lists configuration errors | Fix every variable the message names. See the [configuration reference](/docs/installation/configuration). |
| A pod stays in startup | Another replica holds the migration lock. Read that replica's logs. |
| Large uploads fail | The body size limit and timeouts of the ingress or proxy, and the size of `/tmp` for archives. |
| Uploads fail but downloads work | The key pair lacks write or delete access to the temporary bucket, or the store rejects multipart uploads or checksums. See [Storage](/docs/installation/storage/overview#what-relic-does-not-support). |

## Usage reports

Relic counts downloads and deploys per repository and per user as they
happen, and the worker records each repository's files and bytes every six
hours. **Administration → Usage** shows storage, downloads and deploys by
day, each repository's size and growth over the period, and the top
downloaders and deployers. Administrators and viewers can read it. Usage is
kept for two years.

Print the last 90 days:

```bash
relic usage --days 90
```
