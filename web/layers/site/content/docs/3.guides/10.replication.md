---
title: Replication
description: Copy a repository to or from another server, or keep two servers' repositories alike.
---

A replication links a local repository to a repository on another server, on
a schedule. The worker runs it. It has a direction:

| Direction | What a run does |
| --- | --- |
| `push` | copies the repository's files the target lacks or holds another version of; with `syncDeletes`, deletes the target's files this repository no longer has |
| `pull` | copies the target's files this repository lacks or holds another version of, verifying their checksums; with `syncDeletes`, deletes the files the target no longer has |
| `federated` | pulls, then pushes, so both repositories end up alike |

A federated repository keeps each change: deploys and deletes queue a run as
they are made, and each run also picks up what was missed. With
`syncProperties`, pushes copy properties too. Conflicts resolve by the last write, by the files' modification
times. A delete wins over an older write, and a newer write wins over a
delete. Configure the replication on both servers, each pointing at the
other. A push replication with `onChange` also runs after each change.

The other server is reached through the JFrog® Artifactory® REST API, so it
can be another Relic or an Artifactory.

Relic reaches only public addresses, not loopback, private or link-local ones.
To replicate with a server on the company network, set
`RELIC_UPSTREAM_ALLOW_PRIVATE_ADDRESSES=true` on the server and the worker.

A federated replication:

```yaml
apiVersion: relic.build/v1
kind: Replication
metadata: {name: libs-release}
spec:
  direction: federated
  targetUrl: https://relic-eu.example.com/artifactory/libs-release
  username: replicator
  password: change-me
  schedule: "*/15 * * * *"
  enabled: true
```

Apply it:

```bash
relic apply -f replication.yaml
```

Run it now, whatever its schedule:

```bash
relic replication run libs-release
```
