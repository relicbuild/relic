---
title: Relic Scan
description: Vulnerability scanning of stored artifacts with Syft and Grype, policies, watches and ignore rules.
---

The worker catalogs every scannable file with Syft. Scannable files include package archives
and Docker image manifests. The worker then matches the catalog against Grype's vulnerability
database. If either scanner is missing, Relic Scan turns itself off. The settings are
`RELIC_SCAN_SYFT_PATH`, `RELIC_SCAN_GRYPE_PATH` and
`RELIC_SCAN_VULNERABILITY_DATABASE_DIR`. See the
[configuration reference](/docs/installation/configuration).

## In the UI

- An artifact's **Security** tab shows its findings. For a Docker tag, it shows the image's
  findings. The tab has severity counts, fixable findings, CVSS scores, and where each
  vulnerable package was found.
- The **SBOM** tab lists every component with its licenses. You can filter it by license, to
  components without a license, or to components that violate a license policy. A license
  expression such as `MIT OR Apache-2.0` matches a filter for either license. A violation
  names its policy. Hover over it to see the rule and the watch.
- **Security → Vulnerabilities** lists every finding. You can filter by severity,
  repository and package type, and show only fixable or only known exploited findings.

## Malicious packages

Every scan also reports malicious packages. These are the packages named by
[OpenSSF's malicious-packages data](https://github.com/ossf/malicious-packages), as
advisories with `MAL-` IDs. Relic reads them from OSV every six hours, for npm, PyPI, Maven,
Go, NuGet, crates.io and RubyGems. A malicious package is a critical finding marked
*Malicious*. To see only these findings, use the *Malicious only* filter on the Security page.
When a new advisory arrives, Relic re-checks what it scanned before.

A security policy rule can match only malicious packages. Set *Matches: Malicious
packages* in the policy form, or `malicious: true` in a `Policy` resource. If the rule also
has *Block downloads*, a remote repository stops serving a package as soon as it is reported.

## Reachability (Go)

A vulnerable dependency matters less when no code calls the vulnerable function. For every Go
executable a scan finds, in an archive, an image or on its own, the worker runs
[govulncheck](https://go.dev/blog/govulncheck) on the binary. A Go finding is then:

- **Reachable**: the executable's code calls a vulnerable function. The finding shows the call.
- **Not reachable**: the executable contains the module, but no code calls the vulnerable
  functions.
- **Unknown**: everything else. That covers findings in other languages, Go module sources and
  binaries without build information, since no maintained open-source tool answers the
  question for them.

The badges appear on an artifact's **Security** tab and on the Vulnerabilities page, and a
finding's details show the call. A security rule can skip vulnerabilities no code calls: tick
*Skip Go vulnerabilities no code calls* in the policy form, or set `ignoreUnreachable: true` in
a `Policy` resource. Unknown findings still count.

govulncheck reads the Go vulnerability database, which the worker downloads with Grype's
database from `RELIC_SCAN_GO_VULNERABILITY_DATABASE_URL`. A scan keeps a compact summary of
each Go executable's symbols. When the Go vulnerability database changes, the worker checks
those summaries again without downloading the artifact, so an advisory published later is
classified within a database update.

## Operational risk

Every scan also reports components that carry operational risk, separately from
vulnerabilities:

- **End of life.** The component, or the operating system of an image, is in a release cycle
  past its end of life (*high*), or one that reaches it within 90 days (*low*). Relic matches
  package URLs and operating systems against [endoflife.date](https://endoflife.date)'s product
  data. The worker reads that data every day.
- **Deprecated** and **unmaintained** (*medium*). The package's maintainers deprecated it, or
  its source repository shows no activity for 90 days (the OpenSSF Scorecard *Maintained*
  check). This comes from [deps.dev](https://deps.dev), and is off unless
  `RELIC_DEPS_DEV_URL` is set, because each check sends a package name and version to it.

An artifact's **Security** tab lists its risks below its vulnerabilities, and
**Security → Operational risk** lists them across repositories. When the end-of-life data
changes, Relic assesses what it scanned before again.

A security policy rule can match end of life: set *Matches: End of life* in the policy form,
or `endOfLife: true` in a `Policy` resource. With a minimum severity of *high*, the rule matches
only cycles already past end of life; with *low*, also those ending within 90 days. *Matches:
Unmaintained* (`unmaintained: true`) matches deprecated and unmaintained packages. To accept a
risk, add an ignore rule for the package URL, for example `pkg:pypi/django@4.2.11`, or
`pkg:generic/alpine@3.17.4` for an image's operating system.

List the end-of-life components in one repository:

```bash
relic security risks --kind end_of_life --repository libs-local
```

## Quarantine

Turn on **Quarantine** on a remote repository to hold the files it caches
(the ones Relic Scan scans: archives, packages, images) until Relic Scan has
scanned them and found them not malicious. A held file answers `403` with the
reason, and cannot be copied or moved to another repository either. A file is
released automatically after a clean scan, and later if a match withdraws its
malicious finding.

**Security → Quarantine** lists the held files: waiting for a scan, with a
failed scan, with a skipped scan (files over 2 GiB, which Relic Scan does not
scan), malicious, or rejected. An administrator can release a file, to
serve it whatever its scan says, or reject it, to never serve it. List the
quarantine with the CLI:

```bash
relic security quarantine list
```

Release one file:

```bash
relic security quarantine release maven-remote/org/acme/lib/1.0/lib-1.0.jar --reason "reviewed"
```

Quarantine and download blocking work together: a released file is still
checked against the watches covering its repository.

## Conditions

A security rule can have a condition. A condition is a [CEL](https://cel.dev) expression.
It can use these variables about the finding or issue: `id`, `cves`, `severity`, `cvss`,
`fixable`, `malicious`, `package_name`, `version`, `purl`, `analyzer`, `rule`, `file`,
`reachable` (`reachable`, `not_reachable` or `unknown`), `secret_live`, and, for operational
risks, `eol` and `unmaintained`. It can also use these variables about where it
was found: `repository`, `path` and `build`.

If the rule also has a criterion, such as a minimum severity or a CVSS range, the condition
narrows what the criterion matches. If the condition is the rule's only test, the rule matches
whatever the condition matches.

```yaml
rules:
  - name: critical-outside-our-code
    minSeverity: critical
    condition: '!purl.startsWith("pkg:maven/com.example/")'
    failBuild: true
  - name: secrets-outside-tests
    condition: 'analyzer == "secrets" && !file.endsWith("_test.go")'
    blockDownload: true
```

Relic checks conditions when you save the policy. It refuses a condition that is not valid
CEL, names an unknown variable, or does not return true or false.

## Model files

Loading a pickled machine learning model runs whatever its pickle stream
imports. Relic Scan reads the pickle streams of `.pkl`, `.pickle`, `.joblib`,
`.dill`, PyTorch files (`.pt`, `.pth`, `.bin`, `.ckpt`, zip archives and the
legacy format) and NumPy object arrays (`.npy`), without loading them, and
reports their imports as issues of the `model` analyzer:

| Rule | Severity | When |
| --- | --- | --- |
| `pickle-unsafe-import` | critical | an import that runs code or reaches the system: `os.system`, `subprocess`, `builtins.eval`, `exec`, `socket`, … |
| `pickle-dynamic-import` | high | an import whose name the stream computes, or an unreadable stream in an archive |
| `pickle-unknown-import` | medium | an import outside the libraries models use (PyTorch, NumPy, scikit-learn, …) |

Policies treat model issues like other issues: a security rule with a minimum
severity of critical blocks downloads of a malicious model. The analyzer runs
inside Relic, so it needs no scanner installed. Prefer the `safetensors`
format, which holds no code.

## Secrets and misconfigurations

Relic Scan also looks inside the files it catalogs for two kinds of issues:

| Kind | Found by | Details |
| --- | --- | --- |
| Secrets | [gitleaks](https://github.com/gitleaks/gitleaks) | Keys, tokens and passwords left in files, including files inside archives. Relic records the rule, file and line. It never records the secret. |
| Misconfigurations | [Trivy](https://trivy.dev), with the checks it ships | Helm charts, Kubernetes manifests, Terraform modules, Dockerfiles and container images' configuration (a privileged container, a missing resource limit, an image running as root, …) |

These issues appear under *Secrets and misconfigurations* on an artifact's Security
tab. `relic security report <repository>/<path>` also lists them.

A security policy rule can match these issues to fail builds or block downloads. In the
policy form, set *Matches: Secrets*, or *Misconfigurations* with a minimum severity. In a
`Policy` resource, set `secrets: true` or `misconfigurations: true`.

Each analyzer is off when its binary is missing. The settings for the binaries are
`RELIC_SCAN_GITLEAKS_PATH` and `RELIC_SCAN_TRIVY_PATH`.

### Secret validation

A secret found in a file matters most while its provider still accepts it. With
`RELIC_SECRET_VALIDATION_ENABLED=true`, the worker asks the provider of each secret it finds:

| Provider | Secrets (gitleaks rules) | Asks |
| --- | --- | --- |
| GitHub | personal, fine-grained, OAuth and app tokens | `GET https://api.github.com/user` |
| GitLab | personal access tokens | `GET https://gitlab.com/api/v4/personal_access_tokens/self` |
| Slack | bot and user tokens | `POST https://slack.com/api/auth.test` |
| npm | access tokens | `GET https://registry.npmjs.org/-/whoami` |
| Stripe | secret and restricted keys | `GET https://api.stripe.com/v1/account` |

The outcome is recorded with the issue:

- **Live**: the provider accepts the secret. The issue becomes *critical*.
- **Inactive**: Slack, npm or Stripe refuses it.
- **Not confirmed** (`unknown`): no provider answers for the rule (AWS keys, private keys,
  generic passwords), or a refusal proves nothing. GitHub and GitLab tokens from self-hosted
  servers look like theirs.
- **Check failed** (`error`): the provider did not answer.

Validation is off by default, because it sends each secret to its provider. The secret never
leaves the worker otherwise. Relic does not store or log it, keeps only the outcome, and
writes an audit event (`secret.validated`) for every check. Only the hosts above are
contacted. Checks are spaced half a second apart, and a scan checks at most 50 secrets.
`RELIC_SECRET_VALIDATION_PROVIDERS` narrows the providers asked, for example `github,npm`.

A security policy rule can match live secrets only: set *Matches: Live secrets*, or
`liveSecrets: true` in a `Policy` resource. Conditions can read `secret_live`.

## Deep license scanning

Declared licenses come from package metadata. You can also find licenses in the files
themselves, such as a vendored source file under the GPL or a copied license header. To do
this, install the [ScanCode toolkit](https://github.com/aboutcode-org/scancode-toolkit)
beside the worker. Then set `RELIC_SCAN_SCANCODE_PATH` to its `scancode` binary.

ScanCode reads the text of every file, so it is slow. It is off by default. Relic lists each
license it finds with its file and line. License policies treat these licenses like a
package's own license, so a banned one fails builds or blocks downloads.

## SBOMs

The **SBOM** tab lists the components Relic Scan found. **Export SBOM**
downloads them as CycloneDX 1.6, SPDX 2.3 or the Syft JSON Relic Scan made.

Export an item's SBOM with the CLI:

```bash
relic security sbom export libs-local/app/app-1.4.0.jar --format spdx --file app.spdx.json
```

A build that makes its own SBOM can give it to Relic instead. Relic replaces
the SBOM of the item's content with the document and matches it for
vulnerabilities again. Every file with the same content shares that SBOM, so
this needs deploy permission on each of them, or an administrator:

```bash
relic security sbom import libs-local/app/app-1.4.0.jar build/bom.cdx.json
```

Relic accepts CycloneDX, SPDX and Syft JSON. An imported document is exported
as it was in its own format, and converted to the other one. The Relic API
endpoints are `GET` and `PUT /api/v1/sbom/<repo>/<path>`.

## VEX

Relic imports and exports ignore rules as [OpenVEX](https://openvex.dev) and
[CycloneDX](https://cyclonedx.org/capabilities/vex/) VEX documents:

- *Export VEX* on the Ignore rules page, or `relic security vex export`, writes a document
  for downstream scanners and consumers. It has one `not_affected` statement for each
  vulnerability that a rule ignores in packages. OpenVEX is the default; `--format cyclonedx`
  writes a CycloneDX 1.6 document instead.
- The export can also state the Go vulnerabilities that no code calls (see
  [Reachability](#reachability-go)): choose *With the Go vulnerabilities no code calls*, or
  add `--unreachable`. Each such statement names the scanned file as the product and the Go
  module as its component, with the justification `vulnerable_code_not_in_execute_path`
  (CycloneDX: `code_not_reachable`). Another file may call the same module's vulnerable
  code.
- *Import VEX*, or `relic security vex import`, reads either format. It turns `not_affected`
  and `fixed` statements (CycloneDX: `not_affected` and `resolved`) into ignore rules on the
  packages they name: by package URL, or in CycloneDX by the `bom-ref` or BOM-Link of a
  component in the same document. Each rule's note names the document and its author. Relic records the importing user with the
  rule.

Relic leaves out statements that say *affected* or *under investigation* (CycloneDX:
*exploitable*, *in triage*, *false positive*). The export also leaves out rules that VEX
cannot express: rules without a vulnerability or without a package, and rules limited to
licenses, watches, policies, paths or builds, or that expire, waivers included. Both report
how many they left out.

## Without Internet access

The worker downloads the vulnerability database daily. Without Internet access, you have two
options:

- Mirror Grype's listing. Copy `latest.json` and the archive it names, for example into a
  generic repository. Then point `RELIC_SCAN_VULNERABILITY_DATABASE_URL` at the copy of
  `latest.json`.
- Set `RELIC_SCAN_VULNERABILITY_DATABASE_URL` to `off` and import databases by hand, as
  shown below.

On a machine with Internet access, set the database base URL:

```bash
base=https://grype.anchore.io/databases/v6
```

Then download the latest database archive:

```bash
curl -fsSLo grype-db.tar.zst "$base/$(curl -fsS $base/latest.json | jq -r .path)"
```

Inside the network, import the archive as an administrator:

```bash
relic security database import grype-db.tar.zst
```

Check the database status:

```bash
relic security database status
```

*Import vulnerability database* on the System page does the same as the import command. The
archive stays in object storage until the worker installs it. After that, Relic matches
content scanned against an older database again.

For Go reachability, put a copy of `https://vuln.go.dev/vulndb.zip` in a generic repository,
for example `tools-local/govulndb/vulndb.zip`. Then point `RELIC_SCAN_GO_VULNERABILITY_DATABASE_URL`
at it. The worker downloads the copy as it would the original.

The end-of-life data comes from `RELIC_END_OF_LIFE_URL`, endoflife.date by default. Point it
at a copy, or set it to `off` and import the data by hand. On a machine with Internet access,
download it:

```bash
curl -fsSLo eol.json https://endoflife.date/api/v1/products/full
```

Inside the network, import it as an administrator:

```bash
relic security end-of-life import eol.json
```

Check what the server holds:

```bash
relic security end-of-life status
```

## Policies and watches

- A policy defines what counts as a violation: a minimum severity, or licenses.
- A watch applies policies to repositories or builds. It names local and
  remote repositories, the ones that store files. A download through a
  virtual repository is checked against the member that stores the file, so
  Relic refuses a watch that names a virtual repository or one that does not
  exist.
- A policy can block downloads of violating content.
- A rule that blocks downloads can also block content without a successful
  scan (`blockUnscanned`, **Also block artifacts without a successful scan**
  in the UI): files not scanned yet, files whose scan failed, and files Relic
  Scan skips, such as files over 2 GiB. A skipped file is never scanned, so
  it stays blocked while the rule covers it.

### License policies

A license rule lists either banned or allowed licenses, as SPDX
identifiers. Relic evaluates each component's SPDX license expression against the rule:

| Component license | Banned `GPL-3.0-only` | Allowed `MIT` |
| --- | --- | --- |
| `MIT OR GPL-3.0-only` | no violation: MIT can be chosen | no violation |
| `MIT AND GPL-3.0-only` | violation | violation: GPL-3.0-only is required |
| `GPL-3.0-or-later` | violation: a ban covers every version form | violation |

- A license the scanner could not map to SPDX is compared by name, ignoring case.
- A component without a license is allowed, unless the rule turns **Allow unknown
  licenses** off.
- License policies apply to scanned artifacts, because their SBOM holds each
  component's license. They show on the SBOM tab and can block downloads. Build scans
  (`relic build scan`) report only vulnerabilities.

### Policies as code

Keep policies in your repository as `relic.build/v1` resources, and preview a
change before you apply it. The preview evaluates the policies in a file
against the findings Relic Scan has stored, without storing them, and lists
the files they would raise violations on. A file with one policy:

```yaml
apiVersion: relic.build/v1
kind: Policy
metadata: {name: no-critical}
spec:
  kind: security
  rules:
    - {name: critical, minSeverity: critical, failBuild: true, blockDownload: true}
```

Preview it:

```bash
relic security policy preview -f policies.yaml
```

Apply it once the preview is what you expect:

```bash
relic apply -f policies.yaml
```

A CI job can run both steps: the preview on every merge request, and the
apply on the main branch. For example, in GitLab CI:

```yaml
policy-preview:
  image: relic.example.com/tools/relic:latest
  script:
    - relic security policy preview -f policies.yaml
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

policy-apply:
  image: relic.example.com/tools/relic:latest
  script:
    - relic apply -f policies.yaml
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

### Decisions

Relic records every policy decision that blocks: a blocked download, a build
whose scan fails it, and a promotion a gate refuses. A record names the
subject, the policy, watch and rule, the reason, who the request was for, and
how many times the decision was taken. **Security → Decisions** lists them.
List the blocked downloads with the CLI:

```bash
relic security decisions --kind download
```

## Ignore rules

An ignore rule silences a finding you accept, so it stops counting as a violation. An
ignore rule for a license covers every expression that names the license. For example,
ignoring `GPL-3.0-only` also covers `MIT AND GPL-3.0-only`.

## Waivers

Any signed-in user can ask for an ignore rule with a waiver: the package,
vulnerabilities or licenses it covers, and a reason. Administrators approve it
for 1 to 365 days, and it becomes an ignore rule that expires then, or reject
it with a note. **Security → Waivers** lists your waivers; administrators and
viewers see everyone's.

Request a waiver:

```bash
relic security waiver request --package pkg:npm/lodash@4.17.15 --vulnerability CVE-2020-8203 --reason "the vulnerable function is not reachable"
```

List the pending ones:

```bash
relic security waiver list --status pending
```

The list shows 50 waivers, newest first. List the next 50:

```bash
relic security waiver list --status pending --page 2
```

Approve one for 30 days:

```bash
relic security waiver approve 0192f7a0-5d1e-7c3a-9b2f-6e4d8a1c0b7e --days 30 --note "until the upgrade"
```

## CLI

- `relic security audit` scans a project's dependencies.
- `relic security scan` scans files, images and SBOMs.
- Both commands use the server's vulnerability database and policies. See
  [Scanning and auditing](/docs/cli/security).
- `relic build scan` scans a published build.

To rank findings by real-world risk, see [CVE intelligence](/docs/guides/security/cve-intelligence).
