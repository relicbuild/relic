---
title: Permissions
description: Who may read, annotate, deploy, delete, manage or promote which repositories, builds and releases.
---

A permission grants actions to users and groups. It does this through rules. A permission
has at most one rule for each kind of resource:

| Rule | Covers | Selects |
| --- | --- | --- |
| Repository | items | repositories by name, or all, all local or all remote. Ant-style include and exclude patterns narrow the paths. |
| Build | published builds | patterns matching `<build name>/**` |
| Release | release versions | patterns matching `<release>/<version>` |

Creating a release also needs read on the content it takes in. Promoting one
needs write on the target repositories.

A rule can grant these actions:

- read
- annotate
- deploy (write)
- delete
- promote (releases)
- manage (all of the above)

Administrators can do everything. Other users can do only what a rule, or their
role in a [project](/docs/guides/projects), grants them. An item's
**Permissions** tab shows who may do what on it.

A **viewer** sees the administration and security pages (users, groups,
permissions, policies, findings, system status) without being able to change
them. Auditors and security teams are typical viewers. Turn on **Viewer** for a
user, or **Viewer privileges** for a group to make its members viewers. Being a
viewer grants no access to repository content. Permissions still decide that.

Manage permissions in **Administration → Permissions**, or declare `Permission`
resources and run `relic apply`.
